# Shadow Garden v2.9.0 — Keeper Productivity & Recovery

Shadow Garden v2.9.0 completes the Keeper Productivity & Recovery milestone. It makes repetitive library administration safer and faster while turning catalog recovery from an assumed capability into a tested operational contract.

## Faster, safer Keeper workflows

Garden Keeper can batch-edit existing-series taxonomy, status, translation state, and credits with explicit keep/add/replace/clear semantics and a per-series preview before any write. High-impact batches create a safety snapshot first, preserve unrelated metadata, continue through the canonical catalog owners, and stop rather than silently continuing after a failed save.

Upload review now surfaces high-confidence similar-volume warnings separately from exact-duplicate policy, keeps warnings non-blocking, and provides a concise preflight report with actionable validation findings. Deterministic one-click fixes are limited to transformations that can be explained and reversed instead of guessing at ambiguous metadata.

Bulk artwork workflows reduce repetitive cover/banner maintenance while retaining the existing storage and catalog ownership boundaries. Long maintenance tasks now have an explicit in-tab operation queue so running, queued, completed, and failed work remains visible without pretending browser work continues in the background.

## Catalog recovery becomes a verified contract

Catalog snapshots now have an explicit bounded retention policy and integrity metadata. Recovery audits distinguish checksum-verified snapshots, readable legacy snapshots, missing or malformed material, checksum/size mismatches, and storage-check uncertainty.

A deterministic recovery drill exercises damaged and missing live catalogs against mocked private B2 storage, including emergency restoration from a known-good snapshot. Normal restore continues to preserve a pre-restore safety snapshot when the live catalogs are readable; emergency restore is reserved for genuinely damaged live state.

Destructive cleanup is guarded by **object-complete recovery anchors**. A snapshot counts for destructive safety only when its catalog JSON is recoverable and every EPUB/cover object referenced by that snapshot is still present. Manual backup deletion cannot remove the final object-complete anchor, and Trash purge cannot delete media still required by the selected anchor. Snapshot or media verification uncertainty fails closed when no other complete anchor can be proven.

## Recovery Readiness in Garden Keeper

Maintenance now includes an on-demand Recovery Readiness report. It remains read-only and uses the existing recovery service owners rather than creating another restore/delete/purge path.

**READY** requires both live catalogs to be readable plus a checksum-verified, object-complete retained snapshot. A complete legacy snapshot remains useful recovery material but is labeled **LEGACY** and does not produce READY. Missing recovery media reports **NOT READY**, uncertain storage verification reports **CHECK**, and damaged live catalogs report **RECOVER NOW**.

The report uses read-only B2 credentials, runs only when the Keeper explicitly requests it, rejects duplicate submissions, and discards stale in-flight presentation results after relevant History, Trash, Library, or session changes.

## Reliability contract

The recovery algorithms are exercised against deterministic local/mocked B2 fixtures rather than destructive production recovery. Keeper batch, upload, maintenance, recovery, and readiness contracts are covered by repository/service tests and the permanent real-browser matrix across Chromium desktop, Firefox desktop, WebKit desktop, Chromium Mobile, and WebKit Mobile.

The reusable v2 publisher still requires the exact release commit to pass Verify and Real Browser E2E, match Cloudflare production version/commit metadata, and pass public production smoke before the GitHub release is created.
