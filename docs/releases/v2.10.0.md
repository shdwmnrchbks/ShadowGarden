# Shadow Garden v2.10.0 — Maintenance & Supply Chain

Shadow Garden v2.10.0 completes the Maintenance & Supply Chain milestone. The release does not add a new product surface; it makes dependency maintenance, runtime ownership, documentation freshness, release metadata, and recurring operational verification explicit, reviewable, and self-checking.

## Controlled dependency maintenance

Dependabot is bounded to Shadow Garden's five direct npm dependencies and the reviewed GitHub Actions pins instead of being treated as authority to change the application automatically. Dependency pull requests remain ordinary reviewed changes and must pass the same repository and real-browser release gates as product work.

EPUB.js, AWS/B2, authentication, security-sensitive dependencies, runtime pins, and workflow action changes are never auto-merged merely because an update exists. The maintenance policy distinguishes routine update candidates from heightened-review changes and keeps dependency decisions visible to a human reviewer.

A deterministic dependency-maintenance contract checks the allow-list, pinned workflow actions, and scheduled audit policy. Audit reporting classifies actionable direct/runtime findings separately from inherited or currently non-actionable findings so visibility does not become noisy auto-remediation.

## Runtime and lockfile ownership

The reviewed maintenance baseline uses Node **22.23.2** with npm **10.9.8**. CI and release workflows use the committed lockfiles through `npm ci`, while deterministic checks verify the runtime patch, package-manager declaration, root and E2E lockfile integrity, and registry-backed package metadata.

The release cut synchronizes `package.json`, the root/workspace package-lock metadata, and the deployment version at **2.10.0** without altering dependency resolutions merely to change a release label.

## Documentation and release freshness

Normal `npm run check` now verifies that the active deployment version, current roadmap, documentation index, formal package version, lockfile metadata, changelog head, matching release-notes file, build-context ownership, and reusable v2 publisher remain synchronized.

This turns stale current-version text and stale release metadata into CI failures instead of relying on manual proofreading. It also preserves the intentional distinction between an in-development deployment version and the latest formal release until a release cut makes them converge.

## Recurring baseline health

A monthly/manual **Baseline Health** workflow reruns repository contracts, security checks, the complete deterministic test layers including recovery coverage, a production build, and a realistic-scale Library sanity check. The existing Real Browser E2E workflow also reruns monthly across Chromium desktop, Firefox desktop, WebKit desktop, Chromium Mobile, and WebKit Mobile, retaining the established accessibility and failure-artifact coverage.

The performance tripwire uses a deterministic **300-series synthetic catalog** through the real Library filter/sort/contextual-filter model. Its deliberately broad five-second ceiling detects severe regressions without turning v2.10 into a microbenchmark or speculative performance-engineering project.

Scheduled maintenance verification is read-only with respect to production state. It does not auto-fix dependencies, mutate catalogs, purge storage, perform destructive production recovery, or publish releases.

## Release contract

v2.10.0 keeps the existing v2.0 ownership baseline, private B2/security boundaries, browser-local Reader data, Keeper service ownership, and permanent real-browser release gate intact. The formal release is eligible only after the exact `main` commit passes Verify and the complete Real Browser E2E matrix, Cloudflare production reports the same v2.10.0 version and commit, and the public production smoke checks succeed.
